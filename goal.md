# VibeReview — public-safe status and remaining roadmap

This document records the current evidence boundary. It does not authorize a
provider call, live-corpus use, scientific acceptance, publication, spending,
repository administration, or host-policy change.

## 1. Current truth

The scientific models and transition semantics are frozen. Python remains the
owner of orchestration, validation, canonical identifier allocation,
freshness checks, fallback decisions, and immutable promotion. Provider logic
must stay behind replaceable runtime adapters and must not enter persistent
scientific objects.

The public foundation includes immutable generations, task-owned resource
bundles, private invocation data separated from sanitized engine input,
bounded subprocess execution, output validation, credential leases,
machine-local sandbox qualification, and idempotent accepted-task receipts.
Valid negative or uncertain scientific results are canonical outcomes; they
must never be reclassified as technical failures merely to trigger fallback.

Deterministic CI repair and evidence-collection code exists, but GitHub Actions
are disabled. Administrative evidence is still outstanding: the dedicated
runner must execute the required conformance suite for the exact release
candidate, and branch protection or an equivalent enforceable gate must be
verified by an administrator. Local test results, a hosted capability probe, a
queued job, or an old qualification are not substitutes for that evidence.

There have been no live provider calls, no operator corpus import, no
task-driven scientific run, and no accepted or publication-ready review
output. Synthetic fixtures establish engineering behavior only. No Package C,
provider, corpus, spend, or publication authorization has been granted.

A neutral, one-commit public-safe snapshot is now the root of `origin/master`
in the private hosting repository. Its tree contains the Package B2 and B3
foundations, the public-history guard, and synthetic regressions. It has not
been qualified on an administrative runner or approved for public release.

Provider-managed historical review references remain retained by owner
decision. They are outside the public-safe master ancestry, but their presence
keeps the repository-wide publication gate open.

## 2. Public release and incident gates

Before the private hosting repository is made public or this foundation is
advertised as released:

- Build the public line from a neutral, reviewed base with no ancestry from a
  retired data-bearing line.
- Scan the complete reachable history, current index, and worktree with the
  public path policy and an administrator-held private content denylist.
- Inspect every advertised repository reference, not only the candidate
  branch, and keep corpus, review state, operator configuration, credentials,
  generated prose, links, and submodules out of public history.
- Provider-managed historical references are currently retained by owner
  decision while the repository remains private. Their retention does not
  clear the repository-wide publication gate or recall existing clones.
- A retired provider-managed history contains generated bytecode with an
  embedded local absolute path. It remains outside the public-safe master
  ancestry, but public visibility still requires either retirement and any
  supported hosting-cache purge or an explicit documented exception accepting
  the legacy disclosure risk.
- Retain an administrative incident record without reproducing protected
  content or identifiers.
- Run the deterministic matrix and dedicated sandbox job on the exact
  candidate. Required cases must execute rather than skip, and evidence must
  bind the tested revision, host, profile, policy, and report.
- Enable and verify required checks, review requirements, and restrictions on
  force-push, deletion, and bypass. If the hosting plan cannot enforce them,
  record that as a release blocker.

Qualification is machine- and policy-specific. It cannot be copied between
hosts, reused after relevant code or host changes, or interpreted as a
scientific certification.

## 3. Package B2 foundation — bounded live-engine construction

Package B2 is present in the current private master foundation. It provides a
fail-closed path for explicitly authorized and qualified DeepSeek construction
using bounded request and response handling, credential isolation, redacted
diagnostics, trusted output validation, and the existing runtime precedence
rules.

Construction requires both explicit operator authorization and a current
machine-local qualification matching the requested confinement and network
policy. A permissive host-network profile is not an endpoint allowlist, and
transport permission must not silently enable unrelated browsing or tools.

Protocol-level adapters for other engines may validate inert configuration,
but their live CLI factories remain unavailable. No adapter is enabled by
default, ordinary CI remains credential- and network-independent, and no live
call has been used as acceptance evidence.

Package B2 must remain inactive for live provider use until the current release
candidate is public-safe, its negative construction gates pass, its external
tests remain explicitly opted-in, and the intended execution host has fresh
qualification evidence.

## 4. Package B3 foundation — generic external-library boundary

Package B3 is also present in the current private master foundation. It
supplies a generic, operator-configured external-library boundary with no
bundled checkout, repository location, corpus identity, or operator selection.

Its intended invariants are:

- The operator supplies a full Git commit, superproject gitlink, source paths,
  selection, and finite import budgets outside the public repository.
- Library head and both committed and indexed gitlink entries must agree with
  the pin. Paper, bibliography, and graph reads come from pinned Git objects,
  not mutable worktree files.
- The configured SHA-1 or SHA-256 commit, every traversed tree, and each blob
  consumed are authenticated from their canonical Git object bytes. A prior
  connectivity or filesystem check is defense in depth, not a substitute for
  read-time verification.
- Import is writer-locked, idempotent, no-overwrite, content-addressed, and
  coupled to the immutable generation that owns its selection, provenance,
  lock, and raw Markdown copies.
- Generation mutation remains anchored to the descriptor-opened project,
  state, and generations directories for the full writer transaction; a
  pathname swap cannot redirect `CURRENT` or generation materialization.
- Stable publication identity reuses the canonical Paper while preserving old
  generations. Ambiguous identity or conflicting metadata fails before
  publication of a new generation.
- Retrieval revalidates the generation anchor, corpus lock, graph source, and
  exact raw bytes. It returns bounded runtime candidates only; it does not
  fabricate canonical evidence identifiers or an assessed disposition.
- Ordinary CI uses fictional repositories. A live external-corpus smoke test
  requires explicit opt-in and is inspection-only.

The historical pilot and its generated derivatives are absent and invalidated.
There is no compatibility pilot module, accepted historical result, or
scientific handoff to preserve. Package B3 is not evidence that any real corpus
has been licensed, imported, reviewed, or reproduced.

## 5. Gate before Package C

Package C must not begin until all of the following are true:

- The public release and incident gates above are complete for the exact
  public-safe master and any subsequent candidate changes, including
  administrator-owned runner and protection evidence.
- Packages B2 and B3, together with any subsequent boundary hardening, have
  been independently reviewed and revalidated together.
- The operator has explicitly authorized the provider, host policy, external
  resources, corpus use, output location, and finite run budgets.
- Every input has documented provenance and a redistribution basis, and all
  review state remains outside public source control.
- A recovery rehearsal proves that crashes and validation failures leave
  CURRENT, canonical state, and generation-owned resources mutually
  consistent.

This gate authorizes implementation work only. It does not waive the final
human-review requirement.

## 6. Package C operational sequence

Package C must implement the existing scientific chain without redesigning its
models or allowing provider-specific state into canonical records.

### Project and discovery resources

Initialize an external review project and snapshot every authorized discovery
resource into immutable task-owned content. Parse supplied discovery reports
into proposed themes, claims, terminology, controversies, gaps, and candidate
papers. Discovery provenance remains distinct from publication evidence.

### Corpus challenger

Build bounded paper sketches and compare the selected corpus against discovery
coverage before retrieval queries are finalized. Missing themes, claims,
contradictions, populations, methods, or boundary conditions must be explicit
challenger findings. A negative challenger result is valid canonical state,
not permission to bypass the stage.

### Retrieval and promotion

Generate multi-intent retrieval queries through task contracts. Text and graph
backends may propose raw candidates only. Validate exact source slices,
Unicode code-point offsets, raw content digests, paper ownership, and corpus
provenance before allocating canonical spans. Every promoted span receives
exactly one retrieval disposition in the same coupled promotion; invalid or
over-budget proposals remain in a bounded runtime ledger.

### Evidence assessment and claim packets

Assess promoted spans, aggregate within each paper, preserve contradictions and
independence information, assess and revise claims, and run final claim
validation. Construct each ClaimPacket only from the complete canonical
evidence set and its recorded negative or uncertain findings. RETAIN, NARROW,
REJECT, UNCLEAR, UNSUPPORTED, OVERSTATED, and PARTIALLY_SUPPORTED outcomes stay
canonical and never cause model shopping or fallback.

### Propositions and audits

Generate propositions from validated ClaimPackets, then run proposition-level
content and provenance audits. Audit failures or uncertainty block downstream
eligibility through normal canonical transitions; they do not erase the
finding or invoke a different provider for a preferred answer.

### Rendering and exact assembly

Render only audited propositions, audit each rendered sentence, and assemble
the accepted sentences deterministically. Citation and provenance references
must resolve exactly. No generative transformation may occur after the final
sentence-level semantic boundary, and repeated assembly from the same
generation must be byte-stable.

### Human review and export

Construct a review packet containing the assembled text, claims, evidence,
negative findings, unresolved uncertainties, citations, provenance, run
policy, and audit records. Export remains publication-ineligible until an
authorized human reviews the full packet and records explicit sign-off outside
the model-generated scientific chain. In the absence of that record, the only
valid status is draft or review-required.

## 7. Package C implementation invariants

- All external work is a bounded task proposal. Python performs schema,
  semantic, provenance, freshness, and transition validation before promotion.
- Canonical identifiers are allocated only under the writer lock. Scientific
  state, registries, receipts, and generation-owned resources cross one atomic
  boundary or none do.
- Fallback is limited to eligible technical engine failures. A contract-valid
  scientific result, including a negative or uncertain result, is final for
  that attempt.
- Engine adapters share one conformance contract and one scientific acceptance
  implementation. Cross-engine comparison must not change acceptance
  semantics or select whichever answer is more favorable.
- Corpus size, discovery resources, query volume, candidates, attempts,
  writable entries, bytes, time, and retained diagnostics all have explicit
  finite operator-approved budgets.
- Every stage emits machine-checkable provenance and acceptance artifacts.
  Repeating an accepted input with unchanged semantics is idempotent; changed
  inputs or semantics require explicit reevaluation.
- No database, web UI, workflow engine, multi-agent scientific architecture,
  PDF ingestion, large-corpus expansion, or additional provider is part of
  Package C unless separately authorized after this sequence passes.

## 8. Evidence required to close Package C

Closure requires evidence from the exact reviewed candidate and intended host:

- clean deterministic and sandbox checks with non-skipped required cases;
- qualified, explicitly authorized external-engine construction evidence;
- immutable resource, selection, corpus, and generation provenance;
- challenger coverage including a deliberately omitted-concept regression;
- exact retrieval locators and complete disposition accounting;
- negative, uncertain, contradictory, and stale-input transition regressions;
- idempotent rerun and crash-recovery evidence;
- deterministic sentence assembly with fully resolved citations; and
- a separate human-review record before any publication claim or public
  export.

Until all items are satisfied, the project remains an engineering foundation
on a private, administratively unqualified master, not an operational
scientific review system.
